## Findings

### A. The scope's interface table predates D-53 and D-54

- **Kind:** stale text. **Severity:** low.
- **Where:** `docs/scope.md:96-97`: `OprfService` "return the server's evaluation" (no proof); `LocalKeyStore` lists the device key, the account key version and the sessions' anchors, not the vault's own anchor.
- **Fix proposed:** "the server's evaluation and its proof, checked against the public keys the integration pins in its client code (D-53)"; add "and the vault's own anchor per team (D-54)" to the vault's half.
- **Needs:** an edit.

### B. The integration cost table misses D-54's downloads and writes

- **Kind:** stale text. **Severity:** low.
- **Where:** `docs/integration.md:79-81`: `secureAccount` is "that rotation, then one 2-record write per team", and there is no row for exporting a team.
- **Evidence (read):** since D-54 every re-key, so every team of `secureAccount`, fetches the chain from its roots (`rekeyTeam`); every export fetches it too, and may `replace` one wrap; the vault writes its own anchor locally.
- **Fix proposed:** add "and the version records since each team's floor" to `secureAccount`'s row, and a row for an export (the same download as opening, a possible `replace`, one local write).
- **Needs:** an edit.

### C. §5.11 doesn't say when the same-PIN check is skipped

- **Kind:** spec → code. **Severity:** low.
- **Where:** §5.11 ("A new PIN that opens the current PIN wrap is refused … (one evaluation)"); `vault.ts` `#refuseCurrentPin` returns without refusing when there is no PIN wrap, and when the evaluation is `PIN_RATE_LIMITED` (D-40, TH-44: `secureAccount` must run with the budget spent).
- **Fix proposed:** add "skipped when the current version has no PIN wrap or the PIN budget is spent".
- **Needs:** an edit.

### D. The owner's-anchor repair moves the vault's anchor down; the spec says it never does

- **Kind:** spec → code. **Severity:** low.
- **Where:** D-54 and §5.8 step 3 ("never moving it down"); `member-custody.ts` `recordVaultAnchor(..., replace)` and `recovery.ts` (`ownerAnchor !== undefined`); review 011 listed it as a maintenance condition.
- **Fix proposed:** "never moving it down, except after a repair from an owner's anchor, which replaces it (a forged higher one included)" in §5.8 step 3 and §6.8 step 1. D-54 already says it since 011-C's restatement.
- **Needs:** an edit.

### E. The integration guide doesn't say POPRF key ids start above old ones

- **Kind:** stale text (an integration duty only in D-53). **Severity:** low.
- **Where:** D-53 ("POPRF key ids start above any id used before"); the integration guide's OprfService section has no such line.
- **Evidence (read):** a deployment that reuses key id 1 for POPRF makes a base-mode PIN wrap evaluate under it: the proof verifies, the PIN key differs, and the user sees `WRONG_CREDENTIAL` and spends budget, instead of `UNSUPPORTED_VERSION`.
- **Fix proposed:** add the duty to the OprfService section of the integration guide.
- **Needs:** an edit.

### F. "Doesn't try the upgrade again" is per vault, in memory

- **Kind:** stale text. **Severity:** low.
- **Where:** §5.4; `vault.ts` `#upgradeFailure` (memory only, plan 014).
- **Fix proposed:** "doesn't try it again in that vault (a new page or a new vault tries once more)".
- **Needs:** an edit.
